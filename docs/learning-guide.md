# UrbanTrajectoryDB 新手学习指南

日期：2026-10-02

## 1. 我们现在处于哪一步

这是你的第一个相对完整的工程项目。第一阶段不是马上完成所有功能，而是建立一条可靠的开发闭环：

```text
定义一个小功能 → 先写测试 → 看到测试失败 → 实现功能 → 测试通过 → 记录原因
```

当前只做第一条纵向功能：读取一个 GeoLife 轨迹文件，得到结构化轨迹点。

## 2. 为什么先做单文件解析

完整系统最终需要处理数据库、空间索引、性能实验和 C++ 算法，但它们都依赖可靠的数据。单文件解析具有几个优点：

- 输入和输出明确；
- 不依赖数据库即可测试；
- 容易制造正常和异常样例；
- 能帮助你熟悉 Python；
- 后续批量导入可以直接复用。

## 3. GeoLife 文件的大致格式

GeoLife `.plt` 文件通常先有 6 行文件头，后续每行是一个轨迹点：

```text
39.984702,116.318417,0,492,39744.1201851852,2008-10-23,02:53:04
```

常见字段含义：

1. 纬度；
2. 经度；
3. 未使用字段；
4. 海拔，单位通常为英尺；
5. Excel 风格日期值；
6. 日期；
7. 时间。

第一版解析器只保留：纬度、经度、海拔和时间。

## 4. 第一条测试想证明什么

给定一个包含 6 行文件头和 2 行合法数据的文件，解析器应返回 2 个轨迹点，并正确读取第一条数据的经纬度和时间。

测试不是为了追求覆盖率数字，而是先写清楚“程序应该做什么”。

## 5. 你应该亲自理解的代码

完成第一阶段后，请确保自己能回答：

- 为什么跳过前 6 行？
- 为什么经纬度使用 `float`？
- 为什么时间使用 `datetime`，而不是普通字符串？
- 如果一行字段不够怎么办？
- 纬度和经度的合法范围分别是什么？
- 为什么测试使用很小的固定文件，而不直接使用完整数据集？

## 6. Docker 和数据库是什么关系

Docker Compose 会启动一个独立的 PostgreSQL/PostGIS 容器。它的作用类似一台只运行数据库的小电脑：

- 宿主机端口 `5432` 映射到容器端口 `5432`；
- 数据保存在 Docker volume 中，重启容器不会丢失；
- `database/init/001_schema.sql` 会在数据库第一次初始化时执行；
- PostGIS 为 PostgreSQL 增加空间数据类型和空间函数。

## 7. 今天的验收标准

今天不追求导入完整 GeoLife 数据集。完成以下事项就算成功：

- 项目目录已经建立；
- `docker compose config` 能验证配置；
- Python依赖可以安装；
- 解析器测试先失败、实现后通过；
- Docker Desktop启动后，PostGIS健康检查通过；
- 你能根据本指南说明每个步骤在做什么。
